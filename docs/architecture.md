# Architecture

GeoAPI is a read-only HTTP API over geographic reference data stored in
PostgreSQL with PostGIS.

## System overview

```text
HTTP client
    |
    v
Go API (Chi router and handlers)
    |
    v
pgx connection pool
    |
    v
PostgreSQL + PostGIS
    ^
    |
Bash data pipeline
    |
    +-- downloaded datasets
    +-- Git submodules
```

The API and database run as separate services in `docker-compose.yml`. The API
listens on port 8080. Compose publishes PostgreSQL on host port 5433, while
containers communicate with it on the Compose network as `db:5432`.

## Application components

- `cmd/server/main.go` is the executable entry point. It reads `DATABASE_URL`,
  creates shared handlers, registers routes, and starts the HTTP server.
- `internal/handlers/` contains HTTP validation and SQL queries. There is no
  separate service or repository layer.
- `internal/models/` defines the city, airport, and country JSON response
  shapes.
- `internal/db/postgres.go` creates the pgx pool with 2 minimum connections, 10
  maximum connections, and a one-hour maximum connection lifetime.
- `migrations/` defines the database schema.
- `scripts/` downloads source data, applies migrations, and loads the database.
- `internal/swagger/` is generated by `swag` and ignored by Git. Its `docs.go`
  package registers the OpenAPI specification when imported by the server.

## Request flow

1. Chi matches a request to a handler.
2. The handler parses and validates query parameters.
3. The handler runs SQL directly through the shared pgx pool.
4. PostGIS handles point containment, nearest-neighbour, and GeoJSON
   serialization where required.
5. The handler returns JSON through `go-chi/render`. Most errors are plain-text
   HTTP errors; the health endpoint returns JSON for both healthy and unhealthy
   states.

The service currently has no authentication, authorization, middleware-based
rate limiting, or API version prefix.

## Geographic lookup design

City and airport name searches use PostgreSQL `pg_trgm` similarity. Spatial
lookups use geometries in WGS 84 (SRID 4326):

- cities are points;
- city and administrative boundaries are multipolygons;
- GIST indexes support boundary containment and nearest-city operations.

`GET /boundary` combines four boundary scopes. From narrowest to broadest they
are `city`, `adm2`, `adm1`, and `adm0`. It can resolve a city first, search a
shape by name, resolve a country, or inspect coordinates. See
[API usage](api.md#boundary-resolution) for the selection rules.

## Data flow

The database is not populated by the Go service. `scripts/pipeline.sh` is the
orchestrator:

1. obtain all external datasets;
2. apply pending SQL migrations;
3. load countries, which are referenced by other tables;
4. load cities, administrative boundaries, and airports;
5. load standalone city boundaries.

The pipeline uses local command-line tools for downloads and database access,
and runs GDAL/`ogr2ogr` from a container for geospatial imports. See
[Data pipeline](data-pipeline.md).
